# Rebalance cadence at IBKR, after French tax

Pre-registered 2026-11-26 **before** running any variant. Baseline: TECH,
2.5x, daily 200-day core cut, HIFO, French CTO at Interactive Brokers (2 bps
FX), 5 bps spread, monthly calendar rebalance -> **57.01x after tax**, maxDD
-67.8%, 1,836 trades.

Hypothesis: at IBKR's low FX, faster rebalancing may capture more sleeve
momentum (short-term); slower rebalancing may defer more 31.4% PFU (long-term).
Test both.

Variants:

| name | rule |
|---|---|
| monthly | baseline, month-end calendar |
| bimonthly | every 42 calendar days, days clock |
| quarterly | every 63 days, days clock |
| weekly | every 5 days, lookback 20, skip 2, core lookback 20, vol 10 |
| daily | every day, lookback 10, skip 1, core lookback 10, vol 5 |

Acceptance: after-tax terminal must beat **57.01x**, maxDD must not be worse by
more than 2 pp, and **both** 2018 and 2022 must not be worse than monthly. A
variant that wins only one regime is rejected as path-specific.

Run: `uv run python scripts/cadence.py`.

## Robustness check (pre-registered before the check)

Adopt bimonthly only if **all** hold:

1. Neighbor cadences 35/49/56 days also beat monthly; 42 is not an isolated spike.
2. Every calendar year from 2015-2026 is not worse than monthly by more than 5 pp.
3. A 21-day block bootstrap of daily returns has p5 at least as good as monthly.

Otherwise keep monthly. Run: `uv run python scripts/cadence_check.py`.

## Final verdict: REJECTED, keep monthly

The 42-day 63.36x was a phase spike, not a cadence effect:

- Neighbors: 35d **38.11x**, 49d **20.31x**, 56d 69.83x, 63d 30.87x. Only 42
  and 56 beat monthly; the curve is jagged.
- Annual: 42d is worse by 60.5 pp in 2020, 79.4 pp in 2021, 17.1 pp in 2023,
  12.7 pp in 2026. It fails the 5 pp annual test.
- Calendar bimonthly: Jan/Mar phase **35.52x**, Feb/Apr phase **47.03x**, both
  below monthly 57.01x and 11.5x apart from each other. Phase-dependent.
- Weekly 0.78x and daily -2.65x: faster rebalancing is destroyed by 31.4% PFU
  and costs. The short-term use case is not "trade the same book faster".

Keep the monthly calendar rebalance. The `rebalance_months` / `rebalance_offset`
config stays opt-in (default 1) for future research only.
